<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| YAML file → _ENV_CONFIG | YAML values loaded from disk by PyYAML; user-controlled file content enters _ENV_CONFIG dict |
| workflow JSON → resolve_dynamic_value | Workflow JSON value fields are user-controlled strings; they name keys to look up in _ENV_CONFIG |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-01 | Information Disclosure | _ENV_CONFIG dict | accept | Contains env YAML values (base URLs, config IDs); no more sensitive than what AppConfig already exposes via self.base_url etc. Module-level but not serialized or logged |
| T-10-02 | Tampering | configure_env_resolver() | accept | Module-level singleton; only called once from AppConfig.__init__; no external HTTP vector; test isolation handled by calling configure_env_resolver with test dict in each test |
| T-10-03 | Elevation of Privilege | ${env:KEY} in workflow JSON | accept | Workflow JSON is developer-controlled config, not user-provided web input; attacker with JSON write access already has full workflow control; no privilege escalation beyond existing workflow capabilities |
| T-10-04 | Information Disclosure | ValueError message with Available keys | accept | Key names from env YAML are disclosed in error messages; these are config key names (not values), developer-facing, not user-facing; acceptable tradeoff for debuggability |
</threat_model>
